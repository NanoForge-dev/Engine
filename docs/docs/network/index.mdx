`@nanoforge-dev/network` connects game clients to a game server. It has one library per side:

| Library                | Import from                     | Runs on              |
| ---------------------- | ------------------------------- | -------------------- |
| `NetworkClientLibrary` | `@nanoforge-dev/network/client` | the client (browser) |
| `NetworkServerLibrary` | `@nanoforge-dev/network/server` | the server (Bun)     |

Shared definitions, such as `Channel` and `definePacket`, come from `@nanoforge-dev/network`. Both libraries are reached through `ctx.network`.

Each packet goes on one of four [channels](./packet-framing): reliable or unreliable, ordered or unordered. Reliable channels use a TCP WebSocket; unreliable ones use WebRTC data channels, for low-latency updates such as positions.

A game can also run without a dedicated server: one player's browser hosts the game. See [Peer-to-peer](./network-peer).

## Set up a client and a server

Create the project with a server: `nf new` and answer **yes** to the server prompt. It generates `apps/client` and `apps/server`, each with its network library registered. Put the packet definitions both sides use in a shared file:

```ts shared/protocol.ts
import { Channel, definePacket } from "@nanoforge-dev/network";

export const Input = definePacket<{ key: "up" | "down" }>("input");
export const Move = definePacket<{ id: number; x: number; y: number }>("move", {
  channel: Channel.UnreliableOrdered,
});
```

Register the client library:

```ts apps/client/src/main.ts
import { NetworkClientLibrary } from "@nanoforge-dev/network/client";

const network = new NetworkClientLibrary();
app.use(network);
await app.init(options); // connects to the server
```

And the server library, with the server ECS:

```ts apps/server/src/main.ts
import { EcsLibrary } from "@nanoforge-dev/ecs/server";
import { NetworkServerLibrary } from "@nanoforge-dev/network/server";

const app = NanoforgeFactory.createServer({ tickRate: 60 });
const network = new NetworkServerLibrary();
app.use(new EcsLibrary());
app.use(network);
await app.init(options); // starts listening
```

- The client connects during `app.init`, which rejects when the server can't be reached within 10 seconds.
- Each tick, the network library runs before the ECS: the packets received are ready for your systems.
- `NetworkServerLibrary` needs the Bun runtime, which `nf` uses to run servers.
- With pnpm, a bundled server can fail to start with `Cannot load native addon for node-datachannel`. Add this to `pnpm-workspace.yaml`:

  ```yaml
  publicHoistPattern:
    - "@node-datachannel/*"
  ```

Then send and receive packets: see [Client networking](./network-client) and [Server networking](./network-server). The [pong-network example](https://github.com/NanoForge-dev/examples/tree/main/demos/pong-network) is a complete game.

## Environment variables

Both libraries read their settings from the environment, validated at `app.init`. Set them in the project's `.env` file: prefix a variable with `NANOFORGE_CLIENT_` for the client, `NANOFORGE_SERVER_` for the server, or `NANOFORGE_` for both. See [Environment](../env/index) for where secrets may go.

```dotenv .env
NANOFORGE_CLIENT_SERVER_ADDRESS=127.0.0.1
NANOFORGE_CLIENT_SERVER_TCP_PORT=4445
NANOFORGE_CLIENT_SERVER_UDP_PORT=4444
NANOFORGE_SERVER_LISTENING_TCP_PORT=4445
NANOFORGE_SERVER_LISTENING_UDP_PORT=4444
```

Client variables:

| Variable          | Default | Meaning                                                                        |
| ----------------- | ------- | ------------------------------------------------------------------------------ |
| `SERVER_ADDRESS`  | none    | **Required.** The server's IP address or URL (`ws`, `wss`, `http` or `https`). |
| `SERVER_TCP_PORT` | none    | The server's TCP port. Needed for the reliable channels.                       |
| `SERVER_UDP_PORT` | none    | The server's UDP signaling port. Needed for the unreliable channels.           |
| `WSS`             | `false` | `true` to connect with secure WebSockets.                                      |

Server variables:

| Variable              | Default   | Meaning                                                                                             |
| --------------------- | --------- | --------------------------------------------------------------------------------------------------- |
| `LISTENING_TCP_PORT`  | none      | Port of the reliable channels.                                                                      |
| `LISTENING_UDP_PORT`  | none      | Port of the unreliable channels' signaling.                                                         |
| `LISTENING_INTERFACE` | `0.0.0.0` | Address the server binds to.                                                                        |
| `WSS_CERT`, `WSS_KEY` | none      | Paths to a TLS certificate and its key, for secure WebSockets. Set both or neither.                 |
| `ICE_PORT`            | none      | One fixed UDP port for every WebRTC connection, so a firewall or port forward can allow it.         |
| `ADVERTISE_IP`        | none      | Public IP written into the server's WebRTC candidates, when it runs behind a NAT or in a container. |

Both sides:

| Variable       | Default                       | Meaning                                                                                    |
| -------------- | ----------------------------- | ------------------------------------------------------------------------------------------ |
| `NETWORK_MODE` | `dedicated`                   | `dedicated` or `p2p` (see [Peer-to-peer](./network-peer)).                                 |
| `ICE_SERVERS`  | a list of public STUN servers | STUN and TURN servers for WebRTC: comma-separated URLs (`stun:host:port`) or a JSON array. |

The client fails at start-up when it has neither port, and the server when it has neither listening port. A channel whose port is not set throws when used, except on a [peer-to-peer](./network-peer) host, where every channel works.
